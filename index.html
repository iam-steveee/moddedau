01 / WHAT IS MODDED AU?
01 What Is Modded AU? A detailed explanation based on Innersloth's official modding information. +

PRIMARY SOURCE

Among Us Modding Information

This section summarizes the technical information published by Innersloth for people working with Among Us mods and modded multiplayer. It is a detailed summary, not a replacement for the original documentation.

Open Innersloth's repository ↗

01 · PURPOSE

What Innersloth's documentation is for

Innersloth's repository is intended to share technical information that can help the modding community understand parts of Among Us multiplayer, including information useful when building mods and when playing modded games through Innersloth's backend. The documentation is deliberately focused on the technical interface between a mod and the game's online systems rather than being a general guide to creating a mod from scratch.

Innersloth also links to its modding policy and provides modding@innersloth.com as a contact for modding-related matters. The documentation makes an important distinction: Innersloth does not officially support mods, and requirements, restrictions, or technical behavior can change, particularly when changes are needed for security and player protection.

02 · TWO MOD CATEGORIES

Host-only mods and all-client mods

From the server's perspective, Innersloth describes two broad categories of modded multiplayer.

A

Host-only Mods

Only the host's client is modded. These mods make use of authority held by the host, which can allow modified gameplay while leaving other players on an unmodded client. This makes host-only approaches more accessible because an entire lobby does not necessarily need to install the same mod.

The trade-off is functionality. Because the architecture still gives clients and servers control over particular parts of state, a host-only mod cannot freely change everything about the game.

B

All-client Mods

Every client in the lobby uses the same mod. This gives the mod substantially more freedom to change gameplay because the participating clients can share an agreed understanding of the modified game.

The trade-off is accessibility: players generally need the same mod installed before they can participate in that modded lobby.

03 · MOD REGISTRATION

How Innersloth identifies modded games

Innersloth describes registration as a way to tell the game server that a lobby is modded. Registration can provide special treatment for the modded lobby, particularly around state authority and matchmaking. The documentation separates registration into two mechanisms: a +25 modded flag for host-authority behavior and a Mod GUID for identifying an all-client mod.

Registration is not the same thing as learning how to modify the game itself. Innersloth explicitly says that modders are expected to understand how to change or inject behavior into the Among Us client. The documentation supplies the registration side of that process, but does not teach application modification.

04 · THE +25 HOST FLAG

Host authority mode

Among Us clients contain an integer networking protocol version. Innersloth documents adding 25 to that version as the mechanism that enables a host-authority mode for a lobby.

In that mode, much of the gameplay state that would ordinarily have server authority can instead be handled with host authority. This gives the host's mod more control over the outcome of gameplay features and therefore makes certain gameplay modifications possible.

Important limitations
  • Host authority does not automatically cover every kind of state. Information such as user data and player-protection-related state remains subject to other authority rules.
  • Anti-cheat is relaxed for this mode, but the documentation does not promise that anti-cheat is disabled in every circumstance.
  • Rate limits and other security protections can still apply.

05 · AU MCI

Among Us Modded Client Identification

For all-client mods, Innersloth documents an opt-in system called Among Us Modded Client Identification, or AU MCI. The system lets a mod declare itself as a particular mod during the hosting and matchmaking process.

The documented benefits include searches that look specifically for lobbies running the same mod, lobbies that ordinary unmodded clients cannot join, and special anti-cheat exemptions associated with identified modded games.

Innersloth describes this as a transparency and infrastructure measure rather than official technical support for mods. The stated goal includes helping the modding community while making it easier to maintain stronger anti-cheat behavior for ordinary, non-modded games.

06 · THE THREE AU MCI COMPONENTS

Mod GUID, hosting identification, and matchmaking filters

01

Self-assigned Mod GUID

A mod chooses a unique identifier so the system can distinguish that mod from other modded clients. Innersloth describes these identifiers as version-4 UUID/GUID values.

02

Modded hosting path

A modded host can use the dedicated hosting path associated with its chosen identifier, allowing the game server and matchmaking infrastructure to recognize the lobby as belonging to that mod.

03

Matchmaking filters

Searches can include the mod identifier as a filter so a player can look for lobbies running the same mod instead of receiving unrelated ordinary or differently modded games.

07 · MOD GUID / UUID

Why the identifier matters

The Mod GUID is effectively the identity of an all-client mod within the registration system. A modder assigns one identifier to the mod and should keep using that same identifier throughout the related registration and matchmaking process.

Innersloth points out that these are ordinary version-4 UUID-style identifiers and can be generated using a UUID generator. The important part is uniqueness and consistency, not a special name chosen by Innersloth.

08 · BUILT-IN REGISTRATION HELPERS

Registration support in Among Us 18.0+

Innersloth added built-in client-side registration helpers in Among Us 18.0 and later. The purpose is to make it easier for mod authors to add mod registration without having to recreate the registration mechanism themselves.

The client exposes a registration string and a validation helper. When the registration value is empty or missing, the client behaves as an unregistered game, using ordinary hosting behavior and no mod-specific matchmaking filter. When a valid Mod GUID is set, the client can automatically apply the modded host identification and the corresponding matchmaking behavior.

Innersloth also documents validation behavior for the GUID, including handling empty values and parsing the value into a GUID. Mods that support multiple modes can change their registration value before hosting or searching, using either the registration string or the validation helper described by the repository.

09 · WHAT HAPPENS ON THE NETWORK

Modded host tags and Mod GUID data

At a lower technical level, Innersloth documents a distinct host tag used to mark a modded host. The documented modded host path uses the value associated with the +25 mechanism rather than the ordinary host tag.

For all-client identification, the Mod GUID is included with the host's modded-game information. The server and matchmaking systems can then recognize that the lobby is a modded game and keep it out of normal matchmaking while applying the documented anti-cheat treatment for identified modded games.

10 · MATCHMAKING

Searching specifically for a mod

Innersloth documents a matchmaking filter whose purpose is to match a search against a specific mod identifier. A client can provide the relevant filter and the accepted Mod GUID so the search is restricted to compatible modded lobbies.

This is especially important for all-client mods. If a mod changes the game's rules, network messages, roles, or other shared behavior, allowing an unrelated client into the lobby could produce an incompatible game. Mod-specific matchmaking prevents that situation by separating the modded lobby from ordinary and differently identified games.

11 · +25 AND MOD GUID ARE DIFFERENT

They solve different problems

Innersloth explicitly distinguishes the +25 host-authority mechanism from the Mod GUID identification system. They are not interchangeable names for the same feature.

A mod can use one mechanism or, depending on its architecture and needs, use both. The +25 mechanism concerns host authority, while the Mod GUID identifies an all-client mod for hosting and matchmaking.

12 · HOST-ONLY CHAT COMMANDS

Sending command-like messages to the host

Innersloth documents a host-only communication path for +25 mods. Non-host players can send messages beginning with the mod's command prefix to the host, where the host-side mod can interpret them.

This is useful when a host-only mod needs an interaction from an unmodded player without requiring that player's client to contain the mod. The documentation provides a technical example, but this page intentionally explains the mechanism rather than reproducing the repository's source code.

13 · PACKED GAMEDATATO

Combining several host-to-player messages

Host-only mods can also reduce network overhead by packing multiple GameDataTo messages into one packet. The documented packed-message tag is PackedGameDataTo.

The packing rules are strict: the messages being packed need to be GameDataTo messages, each needs the correct game identifier, and the complete packet including its header must stay within the documented maximum packet size.

Innersloth's documented maximum MessageReader message size, including the header, is 1200 bytes. The same size limit matters when planning packed network messages.

14 · PACKET SEND RATES

Mods still have to respect server-side networking constraints

Connecting to Innersloth's game servers does not mean that a mod gets unlimited network bandwidth. Innersloth states that clients must follow required packet send-rate and packet size constraints.

The documentation notes that the exact requirements for mods were still being determined at the time of publication. Extra room may be possible in some circumstances, but security takes priority and stricter limits can be applied.

Mod developers are therefore encouraged to keep their send rate as low as practical. If a mod genuinely needs a burst of traffic, Innersloth recommends contacting the modding address rather than simply assuming that a higher rate is acceptable.

15 · NETWORKING STRATEGIES

Ways the documentation suggests reducing network pressure

01
Pack GameDataTo messages

Combine compatible host-to-player messages when possible instead of sending many separate packets.

02
Separate reliable and unreliable traffic

Use the appropriate channel for the type of information instead of treating every message as equally important.

03
Spread traffic out

If a burst is unavoidable, distributing packets across frames or time can reduce sudden pressure on the server connection.

04
Use built-in queues and streams

Among Us provides rate-limiting queues and message streams that can help a mod schedule traffic more safely.

16 · RPC QUEUES

Reliable and unreliable RPC delivery

Innersloth documents optimized queues for RPC traffic that is not considered competitive or otherwise latency-critical. The available broadcast mechanisms can use reliable or unreliable delivery depending on what the mod needs.

The practical idea is to avoid forcing every message through the most expensive delivery path. A mod should choose the networking behavior appropriate to the importance and lifetime of the information it is sending.

17 · DATA FLAGS AND MESSAGE STREAMS

Updating only what changed

The documentation also describes DataFlags and message streams as tools for keeping updates efficient. A streamed object can use a dirty flag so that the system knows an update needs to be sent.

This follows the broader networking principle used throughout the documentation: avoid repeatedly sending information that has not changed, and use the game's built-in mechanisms where possible.

18 · PACKET SIZE PLANNING

Keep packets under the documented limit

A practical strategy described by Innersloth is to queue or pack messages until adding another message would exceed the packet capacity. The implementation should combine this with rate limiting so that a mod is controlling both the size and frequency of outgoing traffic.

The documented MessageReader maximum is 1200 bytes including the packet header. This is an important boundary when designing custom network messages and packed GameDataTo data.

19 · THE DOCUMENTATION'S FAQ

What the key points mean together

Is +25 the same thing as a Mod GUID?

No. They are separate systems. +25 is associated with host authority, while a Mod GUID identifies an all-client mod for registration and matchmaking.

Can they be used together?

Yes, depending on the mod's requirements and architecture. Innersloth treats them as separate mechanisms rather than mutually exclusive choices.

Does Innersloth officially support mods?

The repository says no. It provides technical information and registration infrastructure, but explicitly does not promise official technical support for mods.

Does registering a mod teach you how to make the mod?

No. Mod authors still need to understand how to modify the Among Us client. The repository focuses on the registration and networking side of the relationship with Innersloth's backend.
